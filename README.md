# FORMA

Вебсистема інтернет-магазину з каталогом, оформленням замовлень, кабінетом покупця, керуванням запасами та аналітикою попиту. Клієнт працює через REST API; PostgreSQL зберігає товари, користувачів, сесії, замовлення та історію змін.

Стек: React 18, TypeScript, Vite, Node.js, Express 5, PostgreSQL. Проєкт навчальний; документація описує фактичні можливості та порядок експлуатації.

[Запуск](#локальний-запуск) · [Конфігурація](#конфігурація) · [API](#rest-api) · [Тести](#перевірка-якості) · [Розгортання](#розгортання) · [Діагностика](#діагностика)

## Можливості

- Каталог із пошуком, фільтрами, пагінацією та рейтингом реальних продажів.
- Реєстрація, вхід через cookie-сесію та особиста історія замовлень.
- Гостьове оформлення; серверний розрахунок суми, доставки та резервування запасів.
- Захист повторного оформлення через `Idempotency-Key`.
- Керування товарами, архівування, контроль статусів та журнал змін.
- Аналітика за 7, 30 або 90 днів і рекомендації щодо поповнення запасів.
- Черга сповіщень із окремим SMTP-обробником.

Оплата карткою представлена способом оплати й записом платежу зі статусом `PENDING` («Очікується»). Інтеграції з платіжним провайдером і списання коштів немає. Відправлення листів потребує налаштованого SMTP та запущеного worker.

## Локальний запуск

### 1 Отримати залежності

Усі команди нижче виконуються з кореня проєкту.

```bash
cd molytovnyk_practice_catalog
npm ci
npm --prefix server ci
```

### 2 Налаштувати PostgreSQL

У pgAdmin або через `psql` створіть базу, якщо її ще немає:

```sql
CREATE DATABASE forma_store;
```

Скопіюйте шаблон лише якщо `server/.env` ще не налаштовано.

Git Bash / Linux / macOS:

```bash
cp server/.env.example server/.env
```

PowerShell:

```powershell
Copy-Item server/.env.example server/.env
```

Відкрийте `server/.env`, введіть **фактичні** хост, порт, користувача, пароль і назву БД. Параметри мають відповідати підключенню в pgAdmin. Змініть `ADMIN_EMAIL` і `ADMIN_PASSWORD`; пароль адміністратора має містити щонайменше 10 символів.

Шаблон використовує окремі `PG*` змінні. Не додавайте активний `DATABASE_URL` одночасно з ними. Значення шаблону є прикладами для налаштування, а не готовими обліковими даними.

### 3 Підготувати схему

```bash
npm --prefix server run setup
npm --prefix server run db:check
```

`setup` створює схему `forma`, таблиці, довідники, демонстраційні товари й нового адміністратора, якщо задано обидві `ADMIN_*` змінні. Сама база даних має існувати. Повторний запуск не видаляє дані; наявні товари та облікові записи не перезаписуються. Зміна `ADMIN_PASSWORD` у `.env` не змінює пароль уже створеного користувача.

Пул використовує `search_path=forma,public`, щоб не змішувати таблиці з попередніми проєктами у `public`.

### 4 Запустити API та клієнт

Термінал 1:

```bash
npm --prefix server run dev
```

Термінал 2:

```bash
npm run dev
```

| Сервіс | Адреса за замовчуванням |
| --- | --- |
| Інтерфейс | <http://localhost:5173> |
| REST API | <http://localhost:4000/api> |
| Перевірка БД через API | <http://localhost:4000/api/health> |

API перевіряє доступ до БД і основних таблиць перед відкриттям порту. Серверний `dev` запускає Node.js без автоматичного перезапуску; після зміни серверного коду перезапустіть процес. Vite оновлює клієнт під час розробки.

## Конфігурація

Сервер читає `server/.env` незалежно від поточного каталогу термінала. Уже задані системні змінні мають пріоритет. При конфлікті основних налаштувань журнал показує назви змінних без значень. Після змін перезапустіть API і worker.

| Змінна | Призначення |
| --- | --- |
| `PGHOST` | Хост PostgreSQL, наприклад `localhost` |
| `PGPORT` | Порт PostgreSQL, за замовчуванням `5432` |
| `PGDATABASE` | Назва бази, наприклад `forma_store` |
| `PGUSER` | Користувач PostgreSQL |
| `PGPASSWORD` | Пароль користувача; зберігайте у секретах середовища |
| `DATABASE_URL` | Альтернатива всім п’ятьом `PG*` змінним; не комбінуйте обидва способи навіть через системне середовище |
| `PORT` | HTTP-порт API, за замовчуванням `4000` |
| `FRONTEND_ORIGIN` | Дозволений origin для запитів, що змінюють дані; локально `http://localhost:5173` |
| `SERVE_CLIENT` | `1` — віддавати кореневий `dist/` через API; інакше окремий Vite |
| `NODE_ENV` | `production` вмикає атрибут `Secure` для cookie; потрібен HTTPS |
| `ADMIN_EMAIL` | Email нового адміністратора при `setup` |
| `ADMIN_PASSWORD` | Пароль нового адміністратора при `setup`, мінімум 10 символів |
| `SMTP_URL` | Підключення SMTP для окремого worker |
| `MAIL_FROM` | Відправник листів; потрібен разом із `SMTP_URL` |
| `API_PROXY_TARGET` | Адреса API для Vite; задається в **кореневому** `.env`, типово `http://localhost:4000` |

Якщо змінено `PORT`, оновіть також `API_PROXY_TARGET`. Шаблон кореневої конфігурації — `.env.example`. Клієнт звертається до відносних `/api`; секрети БД у браузер не передаються. Для паролів зі спеціальними символами зручніше використовувати окремий `PGPASSWORD` у лапках. У URL такі символи потребують URL-кодування.

## Доступ і сесії

| Роль | Можливості |
| --- | --- |
| Гість | Каталог, рейтинг, оформлення замовлення |
| `customer` | Можливості гостя та власна історія замовлень |
| `catalog_manager` | Власний кабінет, керування товарами, аналітика |
| `order_manager` | Власний кабінет, керування замовленнями, аналітика |
| `admin` | Керування товарами, замовленнями й аналітика |

Реєстрація видає роль `customer`. Публічного API для призначення менеджерських ролей немає. Якщо призначено кілька ролей, API обирає одну за пріоритетом `admin`, `order_manager`, `catalog_manager`, `customer`.

Паролі хешуються через `scrypt` із випадковою сіллю. Cookie `forma_session` має `HttpOnly`, `SameSite=Lax`, строк 7 днів і `Secure` у production. У БД зберігається SHA-256 хеш випадкового токена. HTTP-клієнт має передавати cookie; JWT не використовується. Реєстрація та вхід обмежені спільним лімітом 20 запитів за 15 хвилин на IP в одному процесі.

## REST API

Базовий шлях — `/api`. Тіла запитів — JSON із `Content-Type: application/json`; ліміт тіла 100 KB. Типова відповідь — `{ "data": ... }`; список каталогу додає `meta`. `GET /health` повертає `{ "status": "ok" }`, logout та архівування товару — `204` без тіла.

| Метод і маршрут відносно `/api` | Доступ | Результат |
| --- | --- | --- |
| `GET /health` | Усі | Доступність БД через `SELECT 1` |
| `GET /categories` | Усі | Назви категорій |
| `GET /products` | Усі | Активні товари з пагінацією |
| `GET /products/:id` | Усі | Активний товар або 404 |
| `POST /auth/register` | Усі | Реєстрація та сесія, 201 |
| `POST /auth/login` | Усі | Вхід і сесія |
| `POST /auth/logout` | Усі | Завершення сесії, 204 |
| `GET /auth/me` | Авторизовані | Поточний користувач |
| `POST /orders` | Усі | Оформлення, 201; повтор за ключем — 200 |
| `GET /me/orders` | Авторизовані | Власні замовлення |
| `GET /me/orders/:id` | Власник | Власне замовлення або 404 |
| `GET /admin/products` | `admin`, `catalog_manager` | Увесь каталог із резервами |
| `POST /admin/products` | `admin`, `catalog_manager` | Новий товар, 201 |
| `PATCH /admin/products/:id` | `admin`, `catalog_manager` | Часткове оновлення |
| `DELETE /admin/products/:id` | `admin`, `catalog_manager` | Архівування, 204 |
| `GET /admin/orders` | `admin`, `order_manager` | Усі замовлення |
| `POST /admin/orders/:id/status` | `admin`, `order_manager` | Зміна статусу |
| `GET /admin/analytics?days=30` | Усі три службові ролі | Попит і запаси за період |

Каталог підтримує `page` (від 1), `limit` (1–100, типово 24), `category`, `search`, `minPrice`, `maxPrice`, `inStock=true` і `sort`: `popular`, `rating`, `new`, `price-asc`, `price-desc`. Категорії: `Аудіо`, `Гаджети`, `Дім`, `Подорожі`.

Приклад оформлення:

```http
POST /api/orders
Content-Type: application/json
Idempotency-Key: checkout-example-0001
```

```json
{
  "items": [{ "productId": "nomad-mug", "quantity": 1 }],
  "customer": {
    "firstName": "Іван",
    "lastName": "Коваль",
    "phone": "+380671234567",
    "email": "ivan@example.com"
  },
  "city": "Івано-Франківськ",
  "branch": "Відділення № 2",
  "delivery": "Нова пошта",
  "payment": "Післяплата",
  "comment": ""
}
```

Клієнт передає ID та кількість, а ціни й остаточну суму визначає сервер. Ключ має містити 16–100 літер, цифр, `_` або `-`. Використовуйте один ключ для повторів тієї самої спроби оформлення; інші дані з тим самим ключем дають `409 IDEMPOTENCY_CONFLICT`.

Помилки застосунку мають форму:

```json
{ "status": 409, "code": "INVALID_TRANSITION", "message": "Недозволена зміна статусу." }
```

Коди: `400` — валідація/JSON, `401` — потрібен вхід, `403` — роль або origin, `404` — ресурс, `409` — конфлікт запасу/статусу/ключа, `429` — ліміт входу, `503` — відмова БД, `500` — внутрішня помилка. Відповідь rate limiter може відрізнятися від JSON-формату застосунку. Кожна відповідь має `X-Request-ID`; для 500 та помилок БД ідентифікатор також є в JSON. Драйверні стеки й пароль не повертаються клієнту.

Повні поля та додаткові приклади: [docs/API.md](docs/API.md).

## Правила замовлень і запасів

Доставка розраховується Strategy на основі тарифу з `delivery_methods`. Для «Нової пошти» кошик від **2500 грн включно** має безкоштовну доставку; нижче порога застосовується базовий тариф (початково 120 грн). «Кур’єр» завжди використовує базовий тариф (початково 160 грн). Обчислення патерна виконуються в цілих копійках.

| Поточний статус | Дозволені наступні статуси |
| --- | --- |
| Нове | Підтверджене, Скасоване |
| Підтверджене | Комплектується, Скасоване |
| Комплектується | Відправлене, Скасоване |
| Відправлене | Виконане, Скасоване |
| Виконане | Немає |
| Скасоване | Немає |

State перевіряє перехід після блокування замовлення `FOR UPDATE`. Створення резервує кількість; скасування знімає резерв; виконання зменшує фізичний запас і резерв. Повторне виконання відхиляється до списання. Для скасування потрібна причина щонайменше з трьох символів після обрізання пробілів на краях.

Замовлення, позиції, резерви, історія, платіж і завдання сповіщення записуються в одній транзакції. Помилка відкочує зміни. Історична ціна зберігається в `order_items`; архівування приховує товар із каталогу й зберігає історію. Публічний `stock` означає `stock-reserved`; адміністративна відповідь показує фізичний запас і резерв окремо.

## Аналітика та рейтинг

**Керування → Аналітика** доступне адміністратору та обом менеджерам. Оберіть 7, 30 або 90 днів. Джерело — виконані замовлення, включно з гостьовими. Дата продажу — останній запис переходу у «Виконане»; для старих замовлень без такого запису — дата створення. Виручка використовує історичну ціну позиції та не включає доставку.

Поповнення на 14 днів: `max(0, ceil(units × 14 / days) − availableStock)`. Це підказка за середнім темпом продажів; сезонність і строки постачання не враховані. Приховані товари не рекомендуються до поповнення. За нульових продажів попереднього періоду відсоток зростання дорівнює `null`.

Публічний **«Рейтинг продажів»** (`/#/popular`), блок на головній і сортування «Найбільше купують» враховують продані одиниці за **весь час**. Лідер активного каталогу отримує 5/5, решта — `soldCount / maxSoldCount × 5`, округлено до двох знаків. Однакові продажі дають однакове місце. Без продажів — 0/5 і без місця. Зірки відгуків є окремим показником.

Щоб отримати дані, оформіть замовлення й проведіть його через дозволені статуси до «Виконане». Зміни з іншої сесії підтягуються кнопкою оновлення або повторним відкриттям екрана. Нові та скасовані замовлення не збільшують продажі.

## Перевірка якості

```bash
npm test
npm run build
npm --prefix server run check
```

Після рефакторингу лабораторної 12: **33 успішні тести** — 7 клієнтських і 26 серверних. Збережено всі 25 попередніх тестів, додано 8 перевірок Strategy та State.

API-тести проходять Express, сесії, ролі, SQL, резервування, ідемпотентність, відкат, статуси, рейтинг і аналітику на ізольованому PGlite. Перевірка помилкового пароля використовує драйвер `pg` та імітатор протоколу. Нові тести перевіряють поріг доставки, змінний тариф, підстановку стратегії, некоректні суми, нормальний шлях замовлення, скасування, 28 заборонених переходів і відновлення стану.

Ці перевірки не замінюють тестування розгортання на робочому PostgreSQL, навантаження, SMTP та HTTPS. Автоматичного CI workflow у репозиторії немає; команди запускаються локально або у вашому CI.

## Розгортання

Для роботи з однієї адреси сервер може віддавати зібраний клієнт.

1. Встановіть залежності: `npm ci` та `npm --prefix server ci`.
2. Запустіть тести й `npm run build`. Збірка потребує кореневих devDependencies — не прибирайте їх до цього кроку.
3. Задайте робоче підключення БД, `SERVE_CLIENT=1`, `NODE_ENV=production`, `PORT` і точний HTTPS `FRONTEND_ORIGIN` у секретах середовища або `server/.env`.
4. Для нової БД виконайте `setup`; для наявної — `db:check`. Перед змінами схеми зберігайте резервну копію.
5. За потреби приберіть серверні devDependencies командою `npm --prefix server ci --omit=dev` після тестів.
6. Запустіть `npm --prefix server start` під менеджером процесів. За наявності SMTP запустіть worker окремо.
7. Перевірте `/api/health`, вхід, оформлення та доступ службових ролей через публічну HTTPS-адресу.

Зберігайте `dist/` поруч із `server/` у структурі проєкту. Без `dist/index.html` сервер із `SERVE_CLIENT=1` завершить запуск із поясненням. Для локальної перевірки на HTTP використовуйте `SERVE_CLIENT=1` без `NODE_ENV=production`, щоб браузер міг передавати cookie.

TLS, резервні копії, рестарти процесів і моніторинг забезпечує середовище розгортання. Express у поточному коді не налаштовує `trust proxy`, а rate limiter зберігає лічильники в пам’яті одного процесу. Перед роботою за reverse proxy потрібно узгодити довіру до проксі та обмеження запитів з реальною топологією; для кількох інстансів потрібен спільний механізм ліміту.

## Експлуатація

### Спостереження та сповіщення

`GET /api/health` перевіряє доступність БД, але не SMTP або всі таблиці. Корелюйте помилки через `X-Request-ID` і журнал API. Worker має власний журнал із ID завдання.

Створення та зміна статусу додають запис у `notification_outbox` у тій самій транзакції. Worker забирає завдання через `FOR UPDATE SKIP LOCKED`, повторює невдалі спроби з наростаючою затримкою й позначає `FAILED` після п’ятої невдалої спроби. Завдання `PROCESSING`, що зависли більш ніж на 10 хвилин, повертаються до `PENDING`. Можливе повторне доставлення листа, якщо SMTP прийняв його, а запис `SENT` не зберігся.

Без SMTP черга накопичується. Переглядайте кількість і вік `PENDING`, `PROCESSING`, `FAILED`, доступ до БД та вільне місце. Секрети й рядки SMTP/БД не додавайте до публічних журналів і Git.

### Резервне копіювання та відновлення

Приклад для локального PostgreSQL; підставте свої хост, порт і роль. Ключ `-W` запитує пароль інтерактивно.

```bash
pg_dump -h localhost -p 5432 -U postgres -W -d forma_store -Fc -f forma_store.dump
```

Перевіряйте копію відновленням в **окрему порожню базу**:

```bash
createdb -h localhost -p 5432 -U postgres -W forma_restore
pg_restore -h localhost -p 5432 -U postgres -W -d forma_restore forma_store.dump
```

Після відновлення перевірте схему `forma`, кількість замовлень і цілісність резервів. Для контрольного запуску використовуйте окреме підключення до відновленої бази. Частоту, строк зберігання та шифрування копій визначає середовище експлуатації; автоматизації backup у репозиторії немає.

## Діагностика

| Симптом | Дії |
| --- | --- |
| `password authentication failed` / `DB_AUTH_FAILED` | Звірте хост, порт, роль і пароль саме API у `server/.env`; перевірте системні змінні. pgAdmin може використовувати інше підключення. Перезапустіть API. |
| `Use either DATABASE_URL or PGHOST...` | Залиште один спосіб конфігурації; перевірте також змінні Windows/термінала. |
| `DB_NOT_FOUND` | Створіть базу або виправте `PGDATABASE`; `setup` не створює базу. |
| `DB_SCHEMA_MISSING` | Запустіть `setup`, потім `db:check` з тим самим середовищем. Якщо падає сам setup, дивіться етап і первинну причину: SQL або права ролі. |
| `DB_UNAVAILABLE` / `ECONNREFUSED` | Перевірте службу PostgreSQL, порт, DNS і мережу; Compose використовує 5433 на хості. |
| `EADDRINUSE` | Зупиніть інший API або змініть `PORT` і Vite `API_PROXY_TARGET`. |
| Vite не бачить API | Запустіть API, перевірте `/api/health`, адресу проксі в кореневому `.env` і перезапустіть Vite. |
| Вхід успішний, але сесія зникає | Перевірте передавання cookie, HTTPS при `NODE_ENV=production` та один origin. |
| `ORIGIN_DENIED` | Звірте точний `FRONTEND_ORIGIN`: протокол, хост і порт. |
| Аналітика порожня | Завершіть замовлення дозволеним шляхом; перевірте період і оновіть дані. |
| Листів немає | Перевірте обидві SMTP-змінні, окремий worker та стан outbox. |

Розширена інструкція для Windows/Git Bash: [docs/POSTGRES_WINDOWS.md](docs/POSTGRES_WINDOWS.md).

## Внесення змін

Створюйте окрему Git-гілку; не додавайте власні `.env`, паролі або дампи. Змінюючи бізнес-правила, оновіть відповідні тести й документацію. Перед передачею змін виконайте `npm test`, `npm run build` і `git diff --check`. Репозиторій не містить окремого файлу ліцензії для всього проєкту.
