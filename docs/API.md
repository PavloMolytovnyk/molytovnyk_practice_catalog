# REST API FORMA

Успішні відповіді мають поле `data`, каталог також має `meta` з `page`, `limit`, `total`. Помилка містить `status`, `code`, `message`, а для валідації — `details`. Сесія зберігається в cookie `forma_session` з атрибутами HttpOnly і SameSite=Lax.

## Публічний каталог

`GET /api/products?page=1&limit=24&category=Гаджети&search=Aura&inStock=true&sort=popular` підтримує `minPrice`, `maxPrice` та сортування `rating`, `new`, `price-asc`, `price-desc`. `GET /api/products/:id` повертає опублікований товар.

`sort=popular` тепер сортує за реально проданими одиницями, а `rating` — за окремим полем оцінок відгуків. Відповіді каталогу та окремого товару мають `Cache-Control: no-store`. До кожного товару додано:

| Поле | Значення |
| --- | --- |
| `soldCount` | Сума `order_items.quantity` для замовлень зі статусом «Виконане» за весь час |
| `salesRank` | Місце за кількістю одиниць серед активних товарів із продажами; `null`, якщо продажів немає або товар прихований |
| `popularityScore` | Бал 0–5: `round(soldCount / maxSoldCount × 5, 2)` серед активних товарів; 0 без продажів |
| `popularity` | Для сумісності дорівнює `soldCount`; статичне значення зі старої таблиці більше не використовується |

Наприклад, 100, 50, 50 та 20 одиниць дають місця 1, 2, 2, 3 і бали 5, 2.5, 2.5, 1. При однакових продажах порядок стабільний за `id`; місце однакове. Ранг і бал визначаються до фільтрації, сортування й пагінації, тому фільтр категорії не перетворює друге місце на перше. Товар із нульовим залишком зберігає місце; його можна відфільтрувати через `inStock=true`. Приховані товари не потрапляють у публічний рейтинг і не визначають максимальний бал; історія їхніх продажів лишається доступною адміністрації.

Доступ публічний. Враховуються всі покупці й гості; кошик, резерв, нові, відправлені та скасовані замовлення продажі не збільшують. Історія статусів не приєднується, тож повторні записи історії не дублюють кількість. Повторний запит оформлення з тим самим ключем не створює нове замовлення. Нова покупка впливає на рейтинг після переходу замовлення в «Виконане» й наступного завантаження каталогу. Новий API для рейтингу й міграція БД не потрібні.

## Користувач

```json
POST /api/auth/register
{"firstName":"Іван","lastName":"Коваль","email":"ivan@example.com","password":"correct-horse-123"}
```

`POST /api/auth/login` приймає `email`, `password`. `POST /api/auth/logout` завершує сесію. `GET /api/auth/me` повертає роль. Для `GET /api/me/orders` і `GET /api/me/orders/:id` потрібна автентифікація; останній маршрут ніколи не повертає чуже замовлення.

## Замовлення

```http
POST /api/orders
Content-Type: application/json
Idempotency-Key: 42a35b8b-4d10-4d49-a0ef-12968c543111
```

```json
{"items":[{"productId":"aura-fit","quantity":1}],"customer":{"firstName":"Іван","lastName":"Коваль","phone":"+380671234567","email":"ivan@example.com"},"city":"Івано-Франківськ","branch":"Відділення 12","delivery":"Нова пошта","payment":"Післяплата","comment":""}
```

Тіло не містить цін. Сервер зчитує їх з БД, блокує товари у транзакції, перевіряє залишок і резервує кількість. Доставка «Нова пошта» — 120 ₴ до 2500 ₴, далі безкоштовно; кур’єр — 160 ₴. Відповідь `201` містить `subtotal`, `deliveryFee`, `total` та номер. Повтор того самого ключа і тіла повертає `200` та той самий запис; інше тіло з тим самим ключем — `409`.

## Адміністрування

`GET/POST /api/admin/products`, `PATCH/DELETE /api/admin/products/:id` дозволені `admin` або `catalog_manager`. `DELETE` приховує товар, зберігаючи історію. `GET /api/admin/orders`, `POST /api/admin/orders/:id/status` дозволені `admin` або `order_manager`. Тіло зміни статусу: `{"status":"Підтверджене","note":""}`. Маршрут: Нове → Підтверджене → Комплектується → Відправлене → Виконане; скасування дозволене до виконання, із причиною щонайменше три символи. Скасування знімає резерв, виконання списує фактичний залишок.

## Аналітика товарів

`GET /api/admin/analytics?days=30` доступний ролям `admin`, `catalog_manager`, `order_manager`. Допустимі періоди: `7`, `30`, `90`; типовий — 30 днів. Гість отримує `401`, покупець — `403`, недопустимий період — `400`.

Відповідь `data` містить `period` (`days`, `from`, `to`), `summary` (кількість виконаних замовлень, продані одиниці, виручку, попередні значення, зміну кількості у відсотках і кількість позицій для поповнення), `products` (рейтинг із продажами, запасом і рекомендацією) та `categories` (кількість, виручку й частку продажів).

Враховуються тільки замовлення зі статусом «Виконане», включно з гостьовими. Період визначається датою переходу в цей статус із `order_status_history`; для старих записів без історії використовується `orders.created_at`. Періоди — останні N × 24 години й попередні N × 24 години; межа належить поточному періоду. Нові, зарезервовані та скасовані замовлення не збільшують продажі. Виручка обчислюється з `order_items.price × quantity` без вартості доставки. Приховування товару не прибирає історичні продажі.

`demand=high` означає від 20% проданих одиниць за період; `medium` — є продажі; `none` — немає виконаних продажів. `growthPercent=null`, якщо в попередньому періоді продажів не було, щоб не показувати вигаданий відсоток зростання. Вільний запас = `stock-reserved`. Запропоноване поповнення активного товару = `max(0, ceil(units × 14 / days) − availableStock)`. Приховані товари не рекомендуються до поповнення. Підказки пояснюють підставу: поповнити запас, підтримати популярний товар, стежити за зростанням або перевірити пропозицію без продажів. Це простий прогноз за середнім темпом; він не враховує сезонність чи терміни постачання.

В адмінпанелі відкрийте «Аналітика», оберіть період або натисніть «Оновити дані». Зміна статусу/товару в поточній сесії оновлює статистику; зміни з інших сесій підтягуються кнопкою оновлення або при відкритті вкладки. Обчислення виконуються на сервері, а не з обмеженого списку замовлень у браузері. Аналітика не змінює статичне поле `products.popularity` і не замовляє товари автоматично.

## Збої бази даних

`GET /api/health` повертає `{"status":"ok"}` після успішного запиту до БД. При відмові авторизації, недоступній БД, відсутній базі чи таблицях API повертає `503` з кодами `DB_AUTH_FAILED`, `DB_UNAVAILABLE`, `DB_NOT_FOUND`, `DB_SCHEMA_MISSING`. Помилка містить зрозуміле `message` і `requestId`, який відповідає заголовку `X-Request-ID`. Пароль, рядок підключення і стек драйвера не повертаються клієнту.
