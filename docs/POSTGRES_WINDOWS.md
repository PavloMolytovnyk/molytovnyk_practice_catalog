# PostgreSQL на Windows: виправлення підключення FORMA

Повідомлення `password authentication failed for user "postgres"` означає, що API дістався PostgreSQL, але цей сервер відхилив облікові дані. Успішне підключення в pgAdmin не підтверджує, що Node.js використовує той самий пароль, порт або навіть той самий екземпляр PostgreSQL.

## 1. Звірте підключення

У pgAdmin відкрийте Properties → Connection потрібного сервера. Звірте Host name/address, Port, Username. Базу для застосунку вибирайте ту, де мають бути його таблиці: Maintenance database у властивостях pgAdmin може бути просто `postgres`.

Якщо потрібної бази ще немає, у Query Tool, підключеному до бази `postgres`, виконайте один раз:

```sql
CREATE DATABASE forma_store;
```

Не виконуйте цю команду, якщо база вже існує. Якщо ваша база має іншу назву, вкажіть її в `PGDATABASE`.

## 2. Налаштуйте саме server/.env

Зупиніть старий процес API (`Ctrl+C`). В оновленому проєкті скопіюйте `server/.env.example` у `server/.env`, якщо `.env` ще немає. Якщо є — відредагуйте наявний файл, зберігши свої налаштування адміністратора й SMTP.

```dotenv
PGHOST=localhost
PGPORT=5432
PGDATABASE=forma_store
PGUSER=postgres
PGPASSWORD="ВАШ_ФАКТИЧНИЙ_ПАРОЛЬ_POSTGRESQL"
PORT=4000
FRONTEND_ORIGIN=http://localhost:5173
SERVE_CLIENT=0
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD="ВЛАСНИЙ_ПАРОЛЬ_АДМІНІСТРАТОРА_ВІД_10_СИМВОЛІВ"
```

Замініть усі приклади своїми значеннями. Пароль PostgreSQL — це пароль ролі `postgres`, заданий під час встановлення PostgreSQL або змінений пізніше. Це не пароль входу в pgAdmin і не пароль адміністратора магазину.

Для цього варіанта видаліть активний рядок `DATABASE_URL`. Пароль у `PGPASSWORD` передається як окремий рядок: `@`, `:`, `/`, `%`, пробіли та `#` не потребують URL-кодування. Для `#` і пробілів залиште лапки. Якщо пароль містить подвійні лапки, оберіть одинарні лапки як роздільник, якщо він не містить одинарних.

Для PostgreSQL з `compose.yaml` використайте окремий шаблон `server/.env.docker.example`: порт `5433`, роль `forma`. Ці параметри не потрібно переносити на звичайну локальну інсталяцію PostgreSQL.

API завжди читає `server/.env` відносно власного коду. Це працює і для `npm start`, і для `npm run dev`, і для запуску `node server/src/index.js` з кореня. Системні змінні середовища мають пріоритет; якщо вони конфліктують із `.env`, сервер повідомляє їхні назви без значень.

У PowerShell перевірити наявність таких змінних без виведення паролів можна так:

```powershell
Get-ChildItem Env: | Where-Object { $_.Name -in @('DATABASE_URL','PGHOST','PGPORT','PGDATABASE','PGUSER','PGPASSWORD') } | Select-Object Name
```

Якщо в цій сесії є зайві налаштування від попередніх проєктів, приберіть їх лише з поточного термінала, потім запустіть API в цьому ж терміналі:

```powershell
'DATABASE_URL','PGHOST','PGPORT','PGDATABASE','PGUSER','PGPASSWORD' | ForEach-Object { Remove-Item "Env:$_" -ErrorAction SilentlyContinue }
```

У Git Bash аналогічно:

```bash
unset DATABASE_URL PGHOST PGPORT PGDATABASE PGUSER PGPASSWORD
```

## 3. Створіть таблиці й перевірте API

У корені проєкту потрібні Node.js 20.12+ (або новіша LTS-версія), npm і запущений PostgreSQL. Docker для локальної БД не потрібен.

```bash
npm ci
npm --prefix server ci
npm --prefix server run setup
npm --prefix server run db:check
npm --prefix server run dev
```

`setup` створює окрему схему PostgreSQL `forma`, таблиці та початкові записи, не видаляючи наявні дані. Окрема схема запобігає конфліктам зі старими таблицями `products`, `users` або `orders` у `public`. Команду можна запускати повторно. Адміністратор створюється лише для нової адреси: зміна `ADMIN_PASSWORD` у `.env` не змінює пароль уже створеного облікового запису.

`db:check` показує хост, порт, базу, користувача й перевіряє наявність основних таблиць. Пароль і рядок підключення не виводяться. Якщо налаштування неправильні, команда завершується з помилкою й підказкою.

Сервер пише `FORMA API listening on 4000` лише після успішного підключення та перевірки основних таблиць. Відкрийте `http://localhost:4000/api/health`: має бути `{"status":"ok"}`.

У другому терміналі з кореня:

```bash
npm run dev
```

Відкрийте `http://localhost:5173`. Не відкривайте `dist/index.html` напряму через `file://`: запити API потребують вебсервера.

## 4. Якщо пароль усе ще відхиляється

Підключіться через SQL Shell (psql) до того самого хоста, порту, користувача й бази або виконайте:

```bash
psql -h localhost -p 5432 -U postgres -d forma_store -W
```

Пароль введіть у запиті psql, не в командному рядку. Якщо і psql відхиляє його, перевірте пароль ролі або вибраний екземпляр PostgreSQL. Якщо є кілька встановлених PostgreSQL, порти можуть відрізнятися. Якщо psql працює, звірте `.env`, системні змінні та перезапустіть API.

Якщо pgAdmin уже підключений під роллю, якій дозволено змінювати пароль `postgres`, у Query Tool на правильному сервері можна встановити новий відомий пароль:

```sql
ALTER ROLE postgres WITH PASSWORD 'ВАШ_НОВИЙ_ПАРОЛЬ';
```

Це змінить пароль ролі для інших застосунків, які її використовують. Виконуйте лише якщо хочете змінити саме цей пароль; потім оновіть `PGPASSWORD`. Код проєкту не може автоматично відновити або вгадати пароль вашої локальної БД.

## 5. Фронтенд і порти

Браузер звертається до `/api` на тій самій адресі; Vite передає запити на `http://localhost:4000`. Авторизація через HttpOnly cookie працює через цей самий проксі. У режимі `npm run preview` також налаштовано API-проксі.

Якщо змінюєте порт API, скопіюйте кореневий `.env.example` у кореневий `.env` і змініть `API_PROXY_TARGET`. Перезапустіть Vite. Кореневий `.env` не є місцем для пароля PostgreSQL.

Vite використовує порт `5173` без автоматичного переходу на `5174`: це запобігає розбіжності з `FRONTEND_ORIGIN`. Якщо порт зайнятий, зупиніть попередній Vite-процес.

При збої каталог, кошик і сторінка товару показують стан помилки та кнопку повторного завантаження. Помилка завантаження не видається за порожній каталог або відсутній товар. Якщо API припинив роботу на старті через неправильний пароль, фронтенд повідомляє, що API недоступний; конкретна причина буде в терміналі API. Після виправлення й запуску API натисніть «Повторити завантаження».

## Повідомлення про неготову схему під час setup

У ранній версії проєкту помилки PostgreSQL `42P01` і `42703` під час самої команди `setup` помилково перетворювалися на пораду повторно запустити `setup`. В оновленій версії команда показує етап, SQLSTATE та точне повідомлення PostgreSQL. Таблиці FORMA розміщуються у схемі `forma`, тому таблиці старого проєкту в `public` не заважають встановленню.

Якщо після оновлення команда повідомляє `permission denied for database` або `permission denied to create schema`, запустіть її під власником бази (для типової локальної інсталяції це `postgres`) або в pgAdmin надайте користувачу право створювати схеми в цій базі.
